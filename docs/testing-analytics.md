# Testare și statistici

The static light-only catalog and `statistici.html` share `analytics-ui.js`, `analytics-charts.js` and `testing-analytics.css`, including under `/bio-barrons-umf/`. Question content and answer keys are tracked by the independent UMF 2026 audit in `docs/editorial/umf-2026/README.md`; the runtime preserves stable IDs and historical results.

## Catalog and next study action

The catalog starts with available quizzes, retaining registry order. “Toate capitolele” reveals the full curriculum, including unavailable entries; this is a presentation filter and never changes stored progress. Unstarted rows use “Neînceput” instead of repeated zero metrics. A right-hand progress preview pairs with the introduction on desktop and stacks below it on phones. It shows lifetime distinct verified questions out of all registered questions, a progress bar and a compact real 30-day activity chart. The preview links to the full report; original/corrected scores are not repeated in catalog rows. Repeated verifications contribute to activity without inflating the distinct count.

The report uses three URL-addressable tabs: Rezumat (default), Greșeli (`fila=greseli`), and Istoric (`fila=istoric`). Chapter and period parameters remain compatible; Back/Forward restores them. Summary shows the current full traversal's progress and original score beside the separate corrected score. Date filtering affects historical activity and included traversals, not the current traversal. A new history offers “Rezolvă prima grilă”; a date range without activity keeps current progress visible and permits widening the history period. A one-day observation is compact text instead of an oversized chart; hidden charts unregister before replacement and redraw when their panel becomes visible.

Shared `tokens.css` and `site-redesign.css` provide the requested high-end visual design, while `statistics.css` owns report-specific arrangements: a light structural surface, paired scores, framed primary panels and pill tabs, retaining Figtree and BioMed green. Compact study use overrides decorative large whitespace. The same compact surfaces and controls extend to the catalog and the rest of the static site.

Lesson completion actions link to a quiz only when the canonical chapter registry provides one. Completion copy describes the existing chapter-wide operation; storage behavior is unchanged. Phone notes controls sit in document flow, while desktop notes stay in the topbar.

## Counts and charts

“Grile rezolvate” counts committed verifications, including each later chapter traversal. Ten questions solved twice count as twenty. Correct + wrong equals that total. Accuracy is correct verifications / all verifications. Distinct questions and the current answer-cache completion are separate measures. Empty denominators display a dash. These activity counts live in the collapsed historical activity disclosure. The primary score is the current traversal’s original result, with corrections alongside it. Internal first-event fields remain compatible with older API consumers.

In the multi-day summary, the line connects recorded observations in chronological order, with equally spaced active dates and a fixed 0–100% scale. The activity chart uses columns showing answer counts, split into correct and wrong work. Inactive days/weeks/months are omitted from the axis, points and data table; real 0% results remain visible. With no recorded work, a short empty-state message replaces the axes; a single active day in the summary uses a compact text result. Up to 90 days use daily buckets; longer histories use calendar weeks starting Monday; histories longer than 730 days use calendar months. Grouped percentages use summed counts. Filters retain `?capitol=11&perioada=7`, support 7/30/all, default to all chapters/all time, and preserve browser Back/Forward.

Chart pointer movement uses the nearest real point, keyboard arrows/Home/End navigate points, touch activates values, Escape/outside interaction dismisses them. One compact, viewport-constrained tooltip appears next to its source; collapsible tables provide equivalent data.

### Saved answers and missing dates

The report now defaults to all time. `getReport()` exposes `summary` and `savedResults` in addition to the unchanged dated `totals`/`history` API. Summary counts include verified answers from the identity-scoped answer cache (including Supabase hydration) for which no matching full-quiz history exists. Catalog progress and the collapsed historical totals use this combined report. The primary report separates the current traversal’s immutable initial score from its correction progress. Overlapping cache/history evidence is counted once. An imported answer retained in an earlier closed run remains available after a later retry; mistake-practice events are additional results because they never update the full-quiz cache.

Recovered answers are explicitly undated. They never become IndexedDB attempts, artificial first attempts, or chart points. The 7/30-day filters retain only dated events; the period selector allows switching to all time to include undated saved answers. The all-time history groups these answers separately, showing totals and wrong question numbers. Clearing history still preserves active answers, which therefore remain in the combined report without invented dates.

Saved answer caches remain in `quiz_states`. Detailed history now synchronizes independently as owner-scoped personal records through `user-storage.js` and `cloud-sync.js`; the personal-records database migration is required before publishing this feature. A new device receives actual attempts, traversals and correction rounds, including their original IDs, timestamps and content revisions. Saved totals never manufacture missing history or dates. No production database was changed during implementation.

Regression coverage reproduces 85 synced verified answers (57 correct) plus 35 overlapping dated results: 85 combined results, 50 undated and 35 chart events. It also checks a fresh browser, cloud refresh, offline reload, account isolation, imported retries, practice corrections and all four responsive widths.

## Historical subdivision and diagnostic API

`data/quiz-topics.json` maps each of 611 stable question IDs to one analytical topic; `quiz-index.js` is generated with `quiz.topics` and `question.topicId`. The generator checks full coverage and existing lesson routes/search headings. See `docs/quiz-topics.md` for the classification audit and cross-lesson/mixed decisions. Protected question datasets are not modified.

`getReport({chapterNum,days,topicId})` retains the existing totals/daily/history API and adds `topics`, `errorTypes`, `runs` and `legacyHistory`. The optional topic restricts mistake/history detail, while topic comparisons and chapter totals retain their chapter context. A subdivision becomes eligible for the main descending error-rate ranking after three distinct questions. Smaller samples remain visible; subdivisions with no recorded work are omitted. Error categories with no occurrences are omitted as well. Mixed questions are counted once in their own category.

Mistake details use the latest wrong verification in the period, showing selected, omitted and extra letters. Its resolved state uses the latest recorded result up to the end of the reporting period, so subsequent corrections can be shown separately. Omitted-only / extra-only / both categories partition wrong events; historical outcomes incompatible with available keys remain unknown. New events snapshot the grading answer key. Events without a historical key are explicitly diagnosed against the current key, without rewriting their stored outcome.

## Traversals and restart protocol

The owner-scoped IndexedDB database keeps its established name (`bb.quiz.analytics.v1`, plus the existing owner suffix) and upgrades to schema version 2, adding `runs` alongside `attempts` and `metadata`. Version changes close old connections. Existing events are retained as “Rezultate anterioare”; traversal boundaries and unknown timestamps are never fabricated.

`ensureRun(storageKey)` resumes an active traversal or prepares a new one, preserving preexisting answers with unknown dates. `recordAttempt` optionally accepts `runId` and `answerKey`; within one transaction it deduplicates event IDs and questions in the traversal, stores the event and answer snapshot, and marks the run complete when every question is verified. Calls without a run ID remain supported as legacy events. Empty prepared runs are never shown as saved traversals.

The shared player has one top-level “Reîncearcă tot” control; question-level retry is removed. Answers stay locked after grading until chapter restart. `prepareRestart({storageKey,resetId,answers})` durably archives the full current traversal and writes a pending reset ticket before any answer-cache clearing. `pendingRestart` and `finishRestart` recover the gap between IndexedDB and the separate identity-scoped answer cache after a crash. The player serializes verification/reset through an owner-and-quiz Web Lock where available; transaction guards reject stale runs and pending resets. A rejected history write cannot save the tentative answer: it must reload a matching committed run answer or report a retryable failure. Restart returns to the first range and never creates a visible empty historical run.

A traversal row shows its whole result, even when only some of its activity falls in the selected period. Rows include runs with dated activity or closing within that period. Closed snapshots remain immutable during later traversals. History deletion removes scoped events and runs, preserves active answers, and includes dates outside the selected report period.

Quota/denied storage is visibly reported. Normal verification can use the existing session fallback; restart conservatively refuses to clear answers when it cannot guarantee the archived traversal is durable. IndexedDB remains an owner-isolated local projection and works offline; the durable owner vault supplies the synchronization outbox. Guest history remains local until its authorized account import.

Cache invalidations from cloud acknowledgements, hydration and other tabs do not themselves cancel an in-flight verification. The player reloads the current owner's answers and advances its reset generation only when that owner or the displayed answer state changes. Unsaved empty cards and JSON field order are equivalent to the same saved answers. This prevents a committed history attempt from losing its answer-card update during unrelated synchronization, while actual resets and identity changes retain their guards. `node scripts/quiz-sync-verification-test.mjs` (included in `test:accounts`) reproduces that overlap in both site editions, checks reload without duplicate history and confirms a real concurrent reset still cancels the pending answer.

## Numbered traversals and linked correction rounds

One numbered traversal is the full chapter followed by any number of rounds correcting its original mistakes. `ensureRun` allocates persistent `number` per quiz/owner through metadata; filtering and subsequent practice never renumber it. Existing undated/unordered records remain unnumbered under “Rezultate anterioare”, without guessed boundaries or practice links. Clearing scoped history resets its sequence while preserving current answers.

`ensurePractice(storageKey, restart, sourceRunId)` keeps its first two arguments compatible and accepts an optional source traversal ID. Every chapter question must be verified before correction is eligible. The initial answers remain immutable; a linked child run stores `mode: 'mistakes'`, `sourceRunId`, `roundNumber`, frozen `questionIds` and its own answers. The first round uses the source’s originally wrong IDs; subsequent rounds use only still-wrong IDs from that same source. An unfinished round resumes even if restart is requested. Completed rounds resume for their result view unless restart explicitly starts the next remaining-only round. No empty round counts as an attempt.

The existing quiz URL accepts `?mod=greseli&parcurgere=<sourceRunId>`; bare `mod=greseli` resolves the eligible current traversal. Invalid, incomplete, archived or other-owner sources cannot silently fall back to a different test. A complete saved answer cache can materialize a valid source when practice is opened; merely viewing statistics creates no run. Read-only `quizzes[].current.wrongIds` allows incomplete saved answers to appear in the mistakes view without enabling correction early. `quizzes[].mistakeIds` contains only currently eligible remaining correction IDs.

Reports retain the existing aggregate history semantics and add `quizzes[].activeRunId`, parent `number`, `isCurrent`, `initialComplete`, and `correction`: linked `rounds`, `roundCount`, `currentRoundId`, corrected/remaining IDs and counts, corrected accuracy, completion and eligibility. A correction round counts from its first verified answer. Corrected accuracy uses (original correct + corrected original mistakes) / the whole chapter; original accuracy is untouched. The parent is included in a date range if one of its linked rounds has activity there, and its entire result is displayed. Child rounds are nested inside the parent in the UI, never numbered as separate chapter traversals.

History shows five numbered traversals per page, ascending per chapter. Details show original correct/wrong percentages, weak-topic counts, original wrong question numbers and correction rounds, without question bodies or answer tables. Original wrong IDs remain visible after correction; remaining IDs appear separately. Unlinked older practice remains in legacy history. The same question IDs, authored wording, exact answer-set scoring and ten-question player pages are preserved.

A full restart archives its parent and closes/fences the child in the same durable transaction before clearing the separate answer cache. Every child write revalidates the parent’s owner, active ID, completeness, closed state and pending-reset ticket, plus the active child ID. A stale full or practice tab cannot append results to an archived traversal. Practice never changes the full quiz answer cache or its cloud record. Owner switches remove the previous owner’s player content immediately. Existing worker query fallback supports the source parameter, including first offline entry.

`scripts/quiz-corrections-test.mjs` verifies the core 70% initial → 100% after three linked rounds, stable numbering/filtering, incomplete/archived gating, lazy cache recovery, identity and stale-write guards. `scripts/quiz-mistakes-test.mjs` covers the real player, all registered datasets, shrinking selections, resume, source URLs, late hydration, desktop/mobile and offline entry. `scripts/analytics-progress-ui-test.mjs` verifies the paired immutable scores, numbered history, nested rounds, compact tabs and keyboard/touch behavior. Run `npm run generate`, `npm test`, and `git diff --check` before release.


## Detailed history synchronization (30 September 2026)

`analytics-sync.js` provides pure convergence rules, loaded before user storage, cloud synchronization and `quiz-analytics.js`. Each real row is stored under `bb.analytics.v1:attempt:<id>`, `bb.analytics.v1:run:<id>` or `bb.analytics.v1:metadata:<quiz-key>`, with `version:1`. Existing identifiers, original results, historical answer keys, dates and content revisions are preserved. Attempt IDs deduplicate retries. Full traversals and correction rounds retain their own IDs and parent relationships. Reports still distinguish undated saved answers from dated attempts.

On first use, the adapter merges the current owner's existing IndexedDB rows into the durable vault, then projects merged vault rows back into IndexedDB. Existing guest IndexedDB history is read only when `BBUserStorage.canClaimGuestRecords()` authorizes import into the current account; `claimGuestRecords()` enforces that claim. A second account cannot claim it. The source database is retained, making interrupted migration repeatable without duplicating attempts. Owner changes dispose the previous adapter and reject queued mutations; all asynchronous publishing checks the active owner again.

Offline answers on different questions in the same traversal are merged. For simultaneous verified answers to one question, the earliest actual answer remains the initial result and both variants remain in `answerConflicts`; distinct immutable attempt events remain available. A completed traversal or correction round is never recomputed from the current answer key. Run closure survives stale device updates. Concurrent independently created traversals remain separate records; their existing human-readable numbers are preserved even if independently allocated numbers coincide.

History clearing writes immutable `bb.analytics-clear.v1:<id>` barriers for the selected quiz keys (or all history) and tombstones for known attempts/runs. Every new attempt/run carries the known applicable `clearIds`. Projection suppresses rows missing an applicable barrier, including previously unseen offline rows and old local migrations. An offline device must receive the deletion before creating records in the new history generation; its intervening stale-generation work is retained in storage but excluded from reports. This prevents old history from reappearing. Clearing preserves quiz answer caches and other chapters. A nonexistent chapter is a no-op.

Focused checks: `node scripts/analytics-sync-test.mjs` tests deterministic unions, original-result retention, concurrent answer variants and deletion precedence. `node scripts/analytics-history-sync-test.mjs` uses two Chromium contexts for IndexedDB migration, real timestamp preservation, repeated import, offline history merging, deletion barriers and owner isolation, plus the actual owner-storage adapter for legacy guest claims. These tests use local fixtures, never production Supabase.
